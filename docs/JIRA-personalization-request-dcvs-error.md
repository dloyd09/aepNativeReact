## Summary

Every `personalization.request` event generated by the Adobe Messaging SDK extension is rejected by Edge streaming validation with error `DCVS-1106-400: required key [_adobecmteas] not found`. The events are dead-lettered to `acp_data_error_dcs` and never land in the AEP dataset. This is a schema configuration issue — `_adobecmteas` is marked as required on all event types, but SDK-internal events cannot carry tenant fields. The fix is to mark `_adobecmteas` as optional in the schema.

**Update 2026-05-27 (later same day):** After migrating the AJO Decisioning surface flow from `Optimize.updatePropositions` to `Messaging.updatePropositionsForSurfaces` (see `docs/Decisioning-Channel-Migration.md`), the same DCVS-1106-400 now also fires on the server-side auto-tracked **proposition-send** event for AJO Decisioning items returning from the Edge. The original payload captured for this JIRA carried only an empty IAM surface shell; the post-migration payload (see "Post-Migration Evidence" below) carries a real `weRewards Mastercard` Decisioning proposition with `decisionProvider: EXD` and a `decisionPolicy` strategy. The root cause is identical, but the evidence is now stronger: this is not only an IAM-refresh artifact — it blocks every successful AJO Decisioning delivery from landing in the dataset.

## Root Cause

The bootcamp schema has the `_adobecmteas` field group marked as **required**. This applies the requirement to **all** event types ingested against the schema, including `personalization.request`.

`personalization.request` events are generated **internally by the Adobe Messaging SDK extension** when it fetches in-app messages from AJO (via `Messaging.refreshInAppMessages()` or automatic lifecycle refreshes). The app does not build these events — the SDK emits them directly via its own internal `Edge.sendEvent()` call. There is no public API to intercept these events and inject custom tenant fields before they are sent.

Because the app cannot add `_adobecmteas` to SDK-internal events, and the schema requires it, every `personalization.request` will always fail validation.

## What Was Checked — App-Side Approaches

### Can we inject `_adobecmteas` manually?

No. The `personalization.request` event is emitted by `Messaging.refreshInAppMessages()` internally. The Adobe SDK does not expose a hook to modify XDM on SDK-generated events before they are sent. The app's custom `buildXxxEvent()` builders in `src/utils/xdmEventBuilders.ts` only apply to events the app explicitly constructs and sends via `Edge.sendEvent()`.

### Can we replace `refreshInAppMessages()` with a manual `Edge.sendEvent()`?

No. Even if a correctly-structured `personalization.request` event were sent manually with `_adobecmteas` included, the Messaging extension would not process the AJO response — in-app message delivery depends on the extension handling its own request/response cycle. Bypassing the extension to manually send the request would break message delivery.

### Can we stop the Messaging extension from auto-refreshing?

No. The Messaging extension fetches in-app messages automatically on lifecycle resume (app foregrounded). This behaviour is built into the extension and cannot be disabled without dropping the extension entirely.

### Can we enrich the proposition-send audit event for AJO Decisioning?

No. `Messaging.updatePropositionsForSurfaces(surfaces)` accepts only a string array — there is no XDM payload parameter, unlike the legacy `Optimize.updatePropositions([scope], xdm)`. Verified against `node_modules/@adobe/react-native-aepmessaging/src/Messaging.ts` and the iOS/Android bridge methods.

The native iOS and Android Adobe SDKs expose an `autoCollectPropositionInteractions` flag to disable Edge-side auto-tracking of proposition sends, which would let us emit the audit event manually with `_adobecmteas`. That flag is **not bridged** into `@adobe/react-native-aepmessaging` — no `setAutoTrack`-equivalent for propositions exists on the React Native side (only on `Message` instances, which is for IAM display/dismiss). Bridging it is upstream SDK work.

## Data Impact

**Before the 2026-05-27 migration:** none on active data. Events rejected to `acp_data_error_dcs` were almost entirely the empty IAM-refresh shells — no propositions actually matched (because the request was on the wrong channel), so the audit record carried no useful information anyway. The error was noise in Assurance only.

**After the 2026-05-27 migration:** the rejection now also dead-letters the **server-side audit record of every successful AJO Decisioning delivery** (proposition-send events from `EE-Konductor` with `decisionProvider: EXD`). These are records of legitimate proposition deliveries that the client received and acted on. They do not:
- Land in the AEP event dataset
- Create or update profiles
- Feed into AJO journey entry conditions or proposition-attribution counts
- Affect CJA reporting on proposition-send volumes

The app's manually-sent `decisioning.propositionDisplay` and `decisioning.propositionInteract` events (with `_adobecmteas`) still land cleanly, so display/interact reporting is intact. Only the Konductor-emitted *send* counts are lost.

**Bootcamp confusion:** the repeated DCVS errors are still confusing for students who see them in Assurance and assume their event instrumentation is broken. A `personalization.request` rejection looks identical to a `decisioning.propositionInteract` rejection (which *was* a real bug, now fixed). Students cannot distinguish between expected SDK noise and real instrumentation failures.

## Recommended Fix — Schema Change

Mark the `_adobecmteas` field group as **optional** in the schema.

**Steps:**

1. Open **Adobe Experience Platform** → **Schemas**
2. Open schema: `adb09e8796405ce05b4f780a1116a6fedfa06a85c9a5c747`
3. In the field group list, find `_adobecmteas`
4. Uncheck **Required**
5. Save and publish the schema

**Effect:**
- Events that include `_adobecmteas` (login, logout, commerce, page views, proposition tracking) continue to be validated and accepted exactly as today — the field is still validated when present
- Events that do not include it (`personalization.request`, other SDK-internal events) are accepted without error instead of being dead-lettered
- No app code changes required

## Alternative — Accept and Document

If the schema change is not feasible (e.g. the schema is shared across student sandboxes and changing it has broader impact), the error can be accepted as known noise with the following student-facing guidance added to the bootcamp lab guide:

> **Assurance tip:** You may see `DCVS-1106-400` errors on `personalization.request` events. These are generated automatically by the Adobe Messaging SDK when it checks for in-app messages — your app did not send them and cannot fix them. They do not land in AEP and have no effect on your data or journeys. Focus your validation on `commerce.*`, `mobileApp.navigation.clicks`, `decisioning.propositionDisplay`, and `decisioning.propositionInteract` events.
